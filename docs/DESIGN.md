# diskwhy — scope and MVP design

> Project name `diskwhy`, binary `dwhy`.

## Pitch

**"Why is my disk filling up, and what is safe to remove?"**

A Rust tool for Linux dev boxes, used over ssh. It finds what is big **and what is growing**, explains each item, checks whether it is safe to delete, and removes it the way the owning tool would. It has two interfaces over one engine:

- a **TUI** for people (ratatui; works in any ssh terminal)
- a **JSON CLI** for agents, built around *scan → plan → apply*, where an agent may apply a plan only within limits you set

The idea is to automate what was done by hand on pc-ubuntu on 2026-11-13: 36G free → 166G free, with one root cause (29G of Postgres WAL stuck behind a dead fake-S3 container) that no current cleaner would have found.

## What sets it apart from gdu, lysosome, Mole and others

1. **Growth, not just size.** A scan can keep a snapshot (`--snapshot`), so a later run can show what grew and how fast. The `watch` command measures growth rate within one session, and probes look for known runaway patterns. No background job is needed.
2. **Accounting for hidden space.** It reports the gap between what `df` says is used and what the scan could see (e.g. "35.6G you can't read — rerun with sudo"). It lists Docker images, volumes and build cache by name, counts each hardlinked inode once at its lexicographically smallest path (so per-directory sizes are deterministic for snapshots and `diff`), and subtracts files kept alive by links outside a directory from what a finding claims deleting frees.
3. **Safety checks that look at real state**, not just name patterns:
   - commits that exist on no remote (not only unpushed relative to the upstream branch), in nested repos too
   - uncommitted or untracked files
   - processes whose working directory or open files are inside the target
   - paths a running container or Compose project depends on
   - age gates
4. **Tool-native removal, and stating the cost of recovery.** It uses `cargo clean`, `docker builder prune --filter until=…`, `git worktree remove` without force, `go clean -cache`, and so on. Each finding says what it costs to get back ("reinstall 4 venvs, ~10 min").
5. **Agents can act, but only within a policy.** Plans carry fingerprints and are re-checked when applied. Each risk tier has its own limit, and every action is written to an audit log.

## Decisions taken

| Topic | Decision |
|---|---|
| Audience | Dev boxes like pc-ubuntu first; general servers and homelabs later |
| Language | Rust (2024 edition), Cargo workspace |
| Background job | None in the MVP. Snapshots are taken when you run it. An optional systemd timer can come later |
| Agent authority | May apply a plan, limited by `--max-tier` and the [policy config](#policy-config) (default for agents: the `regenerable` tier only) |
| Independence | Its own scanner; gdu and ncdu are not used |
| Scratch dirs (`stale-tree`) | Both a built-in list and per-directory opt-in, extended by `[scratch]` in the [policy config](#policy-config): `~/scratch`, `~/tmp`, `~/.t3/scratch` and `~/.t3/scratch-*`, plus any directory holding a `.dwhy-scratch` file. Stale means nothing written for 7 days. A location stale as a whole is one finding, otherwise each stale subdirectory is. `/tmp` and `/var/tmp` are left to systemd-tmpfiles, and `~/Downloads` is not scratch. `[scratch] paths` adds locations (described as "configured in policy.toml") and `[scratch] stale_days` sets the age |
| Old tool versions (`tool-versions`) | A version is kept when it is the tool's default, pinned by a project in the scan (`rust-toolchain.toml`, `rust-toolchain`, `.python-version`, `.nvmrc`, `.node-version`) or a rustup override, used by a scanned venv, or the newest installed of its kind; the rest are `rebuildable`. uv's default (the install an unversioned `python`/`python3` shim in uv's bin dir runs) is kept. Node LTS pins (`lts/iron`, `lts/*`) are resolved by codename, and when any Node pin or nvm alias cannot be resolved nothing is reported for that tool. Covers rustup, uv, pyenv, nvm, fnm, `~/sdk` Go SDKs, VS Code Server (all but the most recently used server and its CLI), and Claude Code, Codex and the T3 runtime (all but the version in use, any version a running process executes from per `/proc/<pid>/exe`, and the newest). When the home directory is not scanned, the findings say pins there were not checked |
| Trash (`trash`) | One finding per trash directory (the home trash, and `.Trash-<uid>` or `.Trash/<uid>` at mount roots), removed as a whole so `files/` and `info/` go together; the spec has file managers recreate it. `review`, or `blocked` with a `recent-delete` guard when anything was trashed in the last 7 days, going by the `DeletionDate` in `info/*.trashinfo` |
| Journald (`journald`, 2026-11-24) | Root only, and only with `journalctl` on PATH. One finding for `/var/log/journal` when the scan holds it: archived journal files directly in it or in its subdirectories named by a 32-hex-digit 128-bit ID (`<machine-id>/`), no deeper, started 14 or more days ago. Archived means the names systemd's vacuum parses, `<prefix>@<32 hex seqnum id>-<16 hex head seqnum>-<16 hex head realtime>.journal` and `<prefix>@<16 hex head realtime>-<16 hex>.journal~`; journalctl treats any other `.journal` or `.journal~` file as active and keeps it, and vacuums no other subdirectory (systemd-journal-remote's `remote/` is not touched). Started means what journalctl judges by: the head realtime in the name, or the file's ctime, atime or mtime when earlier. Active journals (`system.journal`, `user-<uid>.journal`), archived ones started within 14 days and other files are not counted. The read follows the walk's rules: directories opened with `O_NOFOLLOW` and checked against the inode just stat'ed, entries `fstatat`ed without following symlinks, symlinks skipped, nothing on another device, regular files only. A hardlinked file counts once, and only when every link to it is an old archived journal; the total is capped at the directory's freeable bytes. Nothing under 1 MiB. `review` (logs cannot be regenerated). The action is `journalctl --directory /var/log/journal --vacuum-time=14d`, which removes only closed archived files, each one whole: a file started more than 14 days ago goes with any newer entries in it, and the reason and recovery text say so. `systemd-journald` always holds the active journals open, so `in-use-cwd`, `in-use-open` and the git guards do not apply; `changed-since-scan` does. Its fingerprint leaves out the newest mtime, which journald's writes to the active journal move all the time; device/inode, the size bucket of the old archived bytes and the removal-root checks still apply |
| Guards | `plan` and `apply` run pre-removal guards. `scan` records guard results from detection only. A home scan takes about 0.4 s, with guard checks taking about 1.3 s for ~200 git worktrees inside findings. See the Explain decision for diagnostic use. A guard that cannot check (git missing or failing, Docker unreachable) blocks. Git guards skip repositories inside a cache (`CACHEDIR.TAG`) and do not apply to `user-cache`, `tool-versions` and `journald` findings. Process guards (`in-use-cwd`, `in-use-open`) do not apply to `journald` (see its decision). Removing a linked worktree or submodule whose git directory is outside the finding keeps its branch's commits in the repository, so unpushed commits there only warn; commits on no branch block. When the git directory is inside the finding (a `.git` directory, a submodule of a superproject in it, a `--separate-git-dir` clone next to it), every commit on no remote blocks. Git directories without a `.git` entry (bare repositories, `--separate-git-dir` targets: a `HEAD` file plus `objects/` and `refs/`) are guarded too: commits on no remote block, and so do work trees outside the finding that use them. A bare or mirror clone has no remote-tracking refs, so it always blocks. One whose `HEAD` the enclosing work tree tracks (a test fixture in a source tree) is part of that repository's history and is skipped. Git runs none of the repository's own programs: `core.fsmonitor` and every configured filter driver are switched off, and `git status` does not look inside submodules (each is checked as a repository of its own), though a submodule checked out at a different commit than recorded still makes the superproject dirty |
| Plans | `dwhy plan` selects by tier ceiling (`--tier`, default `regenerable`, the same as `apply`'s default `--max-tier`) and by finding id or path (`--select`, which lifts the default ceiling; with `--tier` too, a finding must match both). A `--select` entry that names no finding, or only an advice-only one, is an error. Guards run on the selection only. A finding a guard blocks, or a detector-blocked one that `--select` names, goes to the plan's `blocked` list, never its items; advice-only findings are never selected. `plan` exits 2 (the plan is still written) when a finding `--select` named ends up in `blocked`; a finding only the tier ceiling picked that a guard blocks is listed but keeps exit 0, so `dwhy plan -o p && dwhy apply p` works. `--free SIZE` (not with `--select`) sets a goal: of the findings within the ceiling that the guards and identity checks leave eligible, the plan keeps the cheapest tier first and, within a tier, the one that adds the most bytes not already planned (nesting counted as in `plan.bytes`), until at least SIZE is planned. Its `goal` records the target, what was planned, the shortfall, and the count and own bytes of removable findings in each tier above the ceiling; guards do not run on those, so they are listed, never selected. A plan that falls short still exits 0. Each item carries a fingerprint (see [`Fingerprint` in report.rs](../crates/dwhy-core/src/report.rs) and the [filesystem identity checks](#safety-rules-non-negotiable)). The detection that supplies the findings sets `created_at`. A plan expires at the earlier of `expires_at` and one hour after `created_at`. It is refused on another host or uid. See [`Plan` in report.rs](../crates/dwhy-core/src/report.rs) for the plan file contract. Apply rescans the plan's roots, re-detects and re-runs the guards. It acts on the fresh finding with each item's ID and skips it when the fresh detector, path, tier, action or fingerprint differs. An edited plan can go stale but cannot widen what `apply` may do (decided 2026-11-16) |
| Apply | `--max-tier` defaults to `regenerable` for everyone; `--max-tier rebuildable` lets rebuildable items through. A `review` item needs `--confirm <id>` for that item, which is enough on its own (it never lifts a rebuildable item above the ceiling); `blocked` is never applied. Without `--yes` on a terminal, apply lists what it will remove and asks y/N, then rescans and re-checks before removing; only items shown and still ready run. Without `--yes` and with no terminal it refuses (exit 3). `--dry-run` shows everything, removes nothing and writes no audit line. Ready items run deepest path first (pseudo-paths last). A path removal walks from `/` with `O_NOFOLLOW`, [revalidates the root's identity](#safety-rules-non-negotiable), refuses a symlink root or a mount point at or below the root, and stops at an entry on another device; a read-only directory of the user's own inside the root gets `u+rwx` so it can be emptied. Each item gets one [`ApplyOutcome`](../crates/dwhy-core/src/report.rs). The exit code reflects the worst outcome in the report: 1 failed, then 3 refused, then 2 skipped, else 0. The audit log (`$XDG_STATE_HOME/diskwhy/audit.jsonl`, default `~/.local/state/diskwhy/audit.jsonl`, mode 0600) uses [`AuditRecord`](../crates/dwhy-core/src/report.rs). Dispatch requires a successful audit `start` write. If the write fails, apply marks the item failed (decided 2026-11-16). The CLI reports audit write errors on stderr and uses the item outcomes to determine its exit code. Each record also says how apply was invoked: the effective `max_tier`, the `--confirm` ids, `yes` and `tty` (optional fields, absent in older lines; decided 2026-11-23). `dwhy audit` reads the log |
| Policy config (2026-11-23) | Two optional TOML files: `/etc/diskwhy/policy.toml` (root-owned, the machine's ceiling) and `$XDG_CONFIG_HOME/diskwhy/policy.toml` (else `~/.config/diskwhy/policy.toml`). The user file and the command line can only tighten `/etc`, never loosen it. There is no environment variable or flag to skip `/etc`. A file that exists but is unreadable or invalid (bad TOML, unknown key, `max_tier = "blocked"`, `stale_days = 0`) is an error for `scan`, `diff`, `explain`, `plan`, `apply` and the TUI (fail closed, exit 1). See [Policy config](#policy-config) |
| Audit (2026-11-23) | `dwhy audit [--json]` prints the audit log newest first (`--limit N`, default 50, 0 for all). A missing log is `missing: true`, exit 0. Lines that are not records are counted in `malformed_lines` and skipped. Text output escapes every field, since anyone with the user's rights can edit the log |
| Snapshots | Only `scan --snapshot` saves one; `scan` alone still writes nothing. A snapshot is gzip-compressed `diskwhy/v1` JSON (`flate2` with the pure-Rust `miniz_oxide` backend, so the static musl build needs no C compiler; zstd was the first idea, and gzip compresses these files about as well) in `$XDG_STATE_HOME/diskwhy/snapshots/` (default `~/.local/state/diskwhy/snapshots/`), named `<YYYYMMDDTHHMMSSZ>-<scope>[-<n>].json.gz` (`-<n>` only when that second's name is taken), where the scope hashes the host, uid, scan roots (in any order) and `-x`. It records directories of 100 MiB or more (allocated, each hardlinked file counted once), [Docker usage and object records](../crates/dwhy-core/src/report.rs), `df` per filesystem, the detectors that ran, the mount points the walk did not enter, and each finding's id, detector, path, bytes and tier (so growth can be put on findings and `explain` can turn an id into a path). A home directory on pc-ubuntu gives ~1,000 directories and ~140 findings, ~32 KB. Saving prunes, per scope: everything from the last 48 hours is kept, then the newest per UTC day up to 90 days; older ones are deleted. A new snapshot never replaces a file, and pruning removes only regular files with a snapshot name. When saving fails, the scan report is still printed and `scan` exits 1; when only pruning fails after the snapshot is saved, `scan` warns and exits 0 (decided 2026-11-16) |
| Diff | `diff` rescans now and compares with a saved snapshot (`--snapshot` also saves the fresh scan). Without `PATH` it takes the newest snapshot of this host and uid matching `--since`, whatever its roots, and rescans those roots with that snapshot's `-x`, refusing with exit 1 if any recorded root contains U+FFFD (since v1 snapshots write U+FFFD for non-UTF-8 bytes; pass `PATH` explicitly to rescan those bytes); with `PATH`, only snapshots of exactly those roots and `-x` count. `--since` takes `last` (the default), a snapshot id or file (whatever its roots; another host or uid is an error), a duration (the newest at least that old) or an RFC 3339 time (the newest taken by then). Only paths both scans walked are compared: inside the roots of both, and not at or below a mount point either skipped (each snapshot records the mount points its walk did not enter; one saved without that list counts as having skipped none). When the two differ in `-x`, a directory above a mount point one side skipped and the other entered is left out too, since its totals cover different ground; with the same `-x`, neither side's totals include a skipped mount, so a mount that appeared or went away between them leaves its ancestors compared. `notes` names a mount point only when a directory or finding either side recorded was left out because of it. It lists `df` used per filesystem, directories, Docker objects (images and containers by id, volumes by name, build cache; an object whose size the daemon did not compute on either side is left out) and findings by id (one present on one side only is listed only when its detector ran on both), each ranked by bytes per day; changes under `--min-change` (default 10M) are left out. Directory and finding comparisons omit paths containing U+FFFD in either scan. Finding comparisons also omit IDs repeated in either scan. A directory's change goes to the deepest directory that holds most of it: a directory is dropped when the nearest listed directory below it changed by more than half as much in the same direction, so entries can still nest when growth is spread out; `watch` uses the same rule. A directory new above the snapshot's 100 MiB threshold counts the threshold as its earlier size, so its growth is a lower bound (`at_least`). Directories under the threshold are not compared, and `notes` says so (their growth still counts in their parents and in `df`). `scan` and the TUI set finding growth from the newest readable snapshot at least an hour old with the same host, uid, roots and filesystem traversal setting. They match by finding ID using the same path and ID exclusions and report bytes per day. Rates scaled from a shorter window are mostly noise (decided 2026-11-16) |
| Watch | `watch` walks the roots in full at both ends of the window, every directory recorded, and reads Docker image, container, volume and build cache sizes from `GET /system/df` at both ends (volumes under /var/lib/docker are root-only on disk); `--no-docker` skips Docker. The second walk starts `--for` (default 60s, at least 1s) after the first one started, or right away if the first took longer, and rates are bytes per minute over the measured time between the two starts. It also lists `df` used per filesystem. Changes under `--min-change` (default 1M: about 1.4 GiB a day over a minute) are left out. Directories use `diff`'s deepest-directory and path encoding rules. They are compared only where both samples walked, using a fresh mount table for each sample. Paths unreadable or affected by a scan error in either sample, and directories below them, are excluded. Ancestors of paths that fail in only one sample are excluded within both samples' roots too; paths failing in both samples do not by themselves exclude ancestors. A mount skipped in one sample only also leaves out directories above it within both samples' roots, unlike `diff` (decided 2026-11-18). If either sample deduplicated hardlinks and either the failed-path set or skipped-mount set changes, all directory rates are suppressed because attribution can move between siblings; filesystem and Docker comparisons remain available. Notes explain coverage exclusions, naming failed paths and changed mounts when they kept recorded directories out. If scan errors exceed the recorded error paths, `watch` fails instead of comparing unknown coverage. Docker is compared only when figures are available at both ends; otherwise a note explains why. `watch --json` uses the additive `diskwhy/v1` `WatchReport` contract defined in [report.rs](../crates/dwhy-core/src/report.rs). It writes nothing; Ctrl-C ends the process (decided 2026-11-16 and 2026-11-18) |
| Explain | An argument is a finding id if it is exactly `f_` followed by 12 lowercase hex digits. Use `./f_…` for a file named like an id. Other arguments are paths, including Docker pseudo-paths. An id resolves through the newest snapshot of this host and uid that lists it, regardless of roots. If no snapshot lists the id, `explain` exits 1 and suggests passing the path or saving snapshots with `dwhy scan --snapshot`. If snapshot state is unavailable, it still suggests passing the path. Filesystem paths must be UTF-8, including after making them absolute and resolving the parent. Findings with paths that can be confused with a lossy spelling in the walked tree are excluded. Filesystem walks stay on one filesystem. For a directory, detectors normally see the parent walk. This gives `cargo-target` and `node-modules` their project context. A path within reach of a directory `tool-versions` reads versions from (a toolchain, Python, Node, Go SDK, Codex or T3 versions directory one level up, Claude Code's `versions` directory, or the VS Code Server folder up to `cli/servers/<name>`) is walked from that directory instead, files included. That needs every directory from the path up to it to be a directory, not a symlink, on the path's filesystem, none below it a mount point, and the directory to open; otherwise a note says why and the usual rules apply. The command scans `/` and other files and symlinks on their own. It also scans the path on its own and adds a note when the path is a mount point (a mount-table entry or a different device from its parent), its parent cannot be opened, or the parent's walk lacks the path. The reported size is the path's own: a file, or a directory whose wider walk counted a hardlinked file at another path, is measured on its own, as `du` would. A `partial coverage` note names what the walk could not read at, above or below the path, or says the scan had unrecorded errors. Docker pseudo-paths skip the walk and use only Docker detectors; filesystem paths use every detector but Docker's, so they never wait on the daemon. `--detectors` limits the detector selection. The command matches the exact path before applying the scan nesting rule. A saved filesystem finding must match its id at that path. A path query prefers the cheapest tier, then detector name. With no match, it reports any measured size and applies the scan nesting rule to the list of findings below the path (a finding at the path itself, such as another detector's when an id did not match, is not listed). For a direct path query, the text report also says `no detector claims this path`. An id whose saved path contains U+FFFD (v1 snapshots store non-UTF-8 paths lossily) is refused with exit 1. The hint says to pass the path directly if the name really contains U+FFFD, and otherwise, since `explain` takes only UTF-8 paths, to explain its parent directory or rename it to valid UTF-8. For an unmatched saved filesystem id, a metadata lookup of the saved path must report a missing path or a non-directory ancestor to mark it gone. For a saved Docker image or container, explain checks the immutable id recorded in the snapshot before picking a finding. If a rename or retag changes the object's pseudo-path, explain looks for the saved detector's finding at the current pseudo-path and adds a `renamed: now <name>` note. A saved volume matches by name. A different creation time confirms a replacement when both the snapshot and daemon provide one. If the live daemon omits a listed volume's creation time, a matching finding can still be shown. When the snapshot that resolved the id or the growth baseline recorded a creation time, the report omits growth and includes a note about the missing time; when neither did, growth compares by name. Without a saved Docker object id or volume creation time, explain falls back to the saved name, tag or short id and adds an `identity not checked` note when the daemon answers. If the saved object is absent and a different object now holds the saved name or tag, explain reports the saved finding gone. Its note gives the replacement's short id (creation time for a volume) and suggests running `dwhy explain` on the replacement's own pseudo-path (an image's first tag) to inspect it. Explain also omits growth, with a note, when the growth baseline recorded a different object at the finding's pseudo-path than the daemon lists there now (a replacement, a container renamed away with another given its name, a tag moved to another image). The text report gives that reason on its growth line. The saved Docker finding is also gone when the relevant list shows that the object is absent, or for build cache when its list is empty. An explicit empty or null list counts as empty. A missing list or unreachable daemon leaves presence unknown. An existing path without a current finding and an inconclusive presence check each get a note. Probes and guards run only for the selected finding. Growth uses the newest one-filesystem snapshot from the same host and uid that lists the finding and is at least an hour old at the start of the rescan, regardless of roots. Growth applies the finding path and baseline ID exclusions in the Diff decision. The command is read-only and exits 0 when it reports and 1 on an error. See [`ExplainReport`](../crates/dwhy-core/src/report.rs) for the additive JSON contract (decided 2026-11-16 and 2026-11-18). |
| Probes (`postgres-wal`) | Probes add evidence without changing tiers or making findings removable. `scan` runs probes after its selected detectors. `--no-detectors` skips both, and `--detectors` accepts detector names only. `diff`, `watch`, `plan` and `apply` skip probes. See the Explain decision for diagnostic use. For `postgres-wal`, `doctor` checks the requirements of the `docker-volume` detector, which are an accessible Docker socket and `docker` on `PATH`. It skips findings with a blocking `path-not-utf8` guard. It looks at an in-use volume when it is the deepest mount containing a running container's Postgres data directory (`PGDATA` from the container environment, default `/var/lib/postgresql/data`), including tmpfs when comparing mounts. Paths and mount destinations are compared after resolving `.`, `..` and repeated slashes lexically. When several running containers qualify, the first whose psql answers is used, else the first one's API-only evidence. A container is skipped when its server's data directory is on another mount: `data_directory` from the query, or, when psql fails, a `-c data_directory=` or `--data-directory=` option in the container arguments. Diskwhy sends only Engine API GETs (`/containers/json?all=1`, `/containers/{id}/json`, `/containers/{id}/logs` and `/volumes/{name}`). When the `/system/df` listing behind the finding recorded the volume's creation time, evidence is attached only if `/volumes/{name}` still reports that time after probing, so a volume recreated under its name in between is skipped. It runs `docker exec <id> psql` directly as argv with no stdin. The Docker CLI makes the exec API requests. The query uses the local socket. The probe takes the role and database from the container's `POSTGRES_USER` and `POSTGRES_DB`, defaulting to `postgres` and the selected role respectively when unset or empty. It passes the values through the Docker CLI's environment as `PGUSER` and `PGDATABASE`, so only the variable names appear in the host command line. `psql -X -w` skips startup files and password prompts. `PGOPTIONS=-c default_transaction_read_only=on -c statement_timeout=10s -c search_path=pg_catalog` applies session defaults, and the query runs inside `BEGIN READ ONLY`. `PGCONNECT_TIMEOUT` is 5 s. The probe writes nothing to the database or volume. Diskwhy caps stdout and stderr at 1 MiB each and kills the Docker CLI at its 10 s deadline. The query reads WAL and database sizes, archiver statistics, archive settings, `data_directory` and the number of `.ready` files from `pg_ls_archive_statusdir()`. `archive_library` is read with `missing_ok`, so it is null before Postgres 15. `pg_ls_archive_statusdir()` needs Postgres 12; older servers fail the query and get API-only evidence. An empty `archive_command` or `(disabled)` counts as unset. If exec or psql fails or the result cannot be parsed, the probe uses API-only evidence. It reads `archive_mode`, `archive_timeout` and `archive_command` from the container arguments when they start Postgres (a first argument of `postgres`, `postmaster` or `docker-entrypoint.sh`, or options after a container path that is one of those or empty), never from a shell's script, and requests up to 200 timestamped log lines. It demultiplexes stdout and stderr for containers without a TTY. A failed-command detail in the log can supply the command when the arguments give none. The logged failures are marked historical (`historical_command`, with a note) when the arguments set no `archive_command`, an empty one, or one the logged command does not match, reading `%p`, `%f` and `%r` as one word without whitespace and `%%` as `%`. The program and hosts still come from the arguments' command, or from the logged one when the arguments give none. The fallback reports a fixed exec, timeout or psql failure message, with stderr omitted. An unreadable log tail leaves the failure count unknown and reports an HTTP status or a generic daemon error. Invalid, truncated or error frames and invalid TTY log responses make a tail unreadable. A readable tail counts recognized archive command failures at `LOG`, `WARNING` or `FATAL` severity, with an optional SQLSTATE. It reports the latest failure time when available, with a failed WAL file only when one is logged after that failure. Current archiver health remains unknown from logs. The probe infers hosts from supported network URL words (HTTP, HTTPS, SSH, SFTP, FTP, FTPS, rsync, TCP, Postgres and PostgreSQL) and `--endpoint-url`, `--endpoint`, `--host` and `--url` values containing such a URL or `host:port`. It reads the command as shell words without expanding anything: unquoted `#` comments are dropped, the program is the first word after leading assignments and redirections, and a shell's `-c` script (`sh -c '…'`, `bash -lc '…'`) and a quoted `ssh` remote command are read as commands too, two levels deep at most. Quoted arguments of other programs, such as an `echo` message, are not. It skips assignments and the operands of recognized credential and non-destination options (such as `--proxy-user`, `--referer` and `--header`, and curl's `-U`, `-e` and `-H`). Bucket schemes such as `s3://` are excluded. Commands containing `$(`, a backtick or `${` outside a comment yield no targets, including on continuation lines in log details. Lookups match Docker container names, Compose service names, network aliases and DNS names without regard to case. They prefer a shared network, then a running container, then the same Compose project. During host lookup, a 404 skips a disappeared container. Other inspection failures stop further host lookups and preserve results already collected. The diagnosis leads the finding reason. With archiving enabled (`on` or `always`), SQL evidence of failures at or after the latest success, or failures with no recorded success, prompts repair advice. API-only evidence prompts repair advice when the tail contains failures that are not historical, a matched target has stopped, and archiving is not known to be off. Repair advice names an exited or dead target to restore when there is one. With SQL evidence of failure and no stopped match, it suggests fixing `archive_command` and offers starting the target as an option if a host lookup found no match. With no `archive_command` (a failing `archive_library`, say), it suggests repairing the configured archiver. With archiving on and neither `archive_command` nor `archive_library` set, the diagnosis says so, failures prompt no repair advice, and heavy WAL prompts advice to set one or turn `archive_mode` off. When SQL evidence shows no current failure and WAL is at least 1 GiB and more than 4× the data with archiving on, the advice is to check replication slots, `max_wal_size` and the archiver. The diagnosis then says `nothing archived since <time>` (or `nothing archived yet`) and gives the `.ready` backlog, since `pg_stat_archiver` does not count an archive command that exits above 125 or dies on a signal. With a backlog, the advice starts with checking for a crashing or slow archiver; without one, the diagnosis points at replication slots and `max_wal_size`. The SQL path never reads the log tail. When `POSTGRES_INITDB_WALDIR` names a path on another mount than the volume, the evidence sets `wal_on_other_mount`, a note and the diagnosis label the WAL figure as the cluster's, and WAL prompts neither repair nor heavy-WAL advice for the volume. Otherwise the detector's action stands. The advice says WAL is freed or recycled at the next checkpoint once it is archived and no replication slot needs it; a recycled segment keeps its space. The tier stays `review` and WAL advice warns against removing the volume (decided 2026-11-16 and 2026-11-18; issue #48 follow-ups 2026-11-22). |

### Recommendation: root vs user

- **Run as your user by default.** Everything works without sudo.
- **Report the gap.** If `df` used minus scanned bytes is larger than a threshold (when a whole-filesystem mount point is scanned), show an "unaccounted N GB" item with the likely places (`/var/lib/docker`, `/var/lib/containerd`, `/var/log`, other users' homes) and the command to rerun with sudo (using the running binary's absolute path, since `sudo` resets `PATH`). Known limitation: when a scan has both a whole-filesystem mount point and a non-recursive bind mount of a directory that another mount covers in the whole walk, the bind-mount root's bytes are left out of `scanned` (the whole walk is taken to reach that location, to avoid counting it twice), so what the covering mount hides stays in `unaccounted`; the `shadowed-by-mount` hint still points at it.
- **Running under sudo is supported, not required.** System detectors (journald vacuum, old snap revisions, old kernels, apt cache) are enabled only when running as root.
- **Never touch other users' files** unless running as root *and* `--all-users` is passed.
- **Docker** is read through the Engine API over its Unix socket (`GET /system/df`, `/info`) for exact bytes—including when Docker uses the containerd image store in `/var/lib/containerd` rather than `/var/lib/docker`—while suggested removals use the CLI. Under the containerd image store, locally built images also carry a `RepoDigest`, so image recovery text says `docker pull <tag> (or docker build)`. Being in the `docker` group is already root-equivalent, so Docker findings default to the `review` tier. The exception is build cache unused for a week, which is `regenerable`: it is a cache, `docker builder prune --filter until=168h` removes only those records, and the cost is re-running build steps (issue #2).

### Recommendation: static binary

- **Ship static musl builds** (x86_64 and aarch64) as GitHub release assets. Rust makes this cheap, and ssh boxes run all sorts of glibc versions. A `.deb` and `cargo install` come later.
- **No runtime dependencies are required.** It calls optional external tools (`git`, `docker`, `cargo`, `go`, `journalctl` and the package managers whose caches `user-cache` reports; `dwhy doctor` lists them all) when they exist. A missing tool disables only the detectors and probes that depend on it, and `dwhy doctor` explains why.
- **Shell out to `git`** instead of linking libgit2/gix. This matches git's own behaviour exactly (worktrees, submodules, safe.directory) and keeps the binary small.

## Main concepts

- **Scan.** A parallel, single-filesystem walk (`-x` is the default and accepted as a no-op; `--cross-filesystems` crosses mounts). A btrfs subvolume that is not mounted on its own has its own `st_dev` but is the same filesystem, so `-x` enters it if it is writable. A snapshot or read-only subvolume (as the unprivileged `BTRFS_IOC_GET_SUBVOL_INFO` reports) is never entered, with or without `--cross-filesystems`, and is listed in `skipped_mounts` with reason `btrfs_snapshot`: a snapshot shares its extents with its source, so walking both would count them twice, and nothing in a read-only subvolume can be removed. A scan root inside one is still scanned, and a subvolume the user cannot open is entered and recorded as unreadable. It counts each hardlink once by `(dev, inode)` (attributed to its lexicographically smallest path) and records allocated (`st_blocks * 512`) vs apparent (`st_size` of non-directories; directories count 0, as in GNU `du >= 9.2`) bytes. Unreadable directories are recorded, not skipped silently. The walk keeps one in-memory node per directory plus multiply-linked inodes (~90 MiB RSS for `/` on pc-ubuntu; see #16).
- **Detector.** Recognises one kind of reclaimable thing and turns it into a **finding**, e.g. `cargo-target`, `node-modules`, `venv`, `user-cache` (go/npm/uv/pip/HF/playwright), `git-worktree`, `stale-tree` (scratch dirs by age), `tool-versions`, `trash`, `docker-image`, `docker-build-cache`, `docker-container`, `docker-volume`, `journald`.
- **Probe.** Adds evidence that explains why a finding is big or growing. See [Decisions taken](#decisions-taken).
- **Guard.** A safety check with a pass, warn or block result. Examples include `git-unpublished`, `git-dirty`, `git-linked-worktrees`, `in-use-cwd`, `in-use-open`, `container-mount`, `recent-write`, `git-ignored-only` (not built yet), [`path-not-utf8`](#safety-rules-non-negotiable) and [`changed-since-scan`](#safety-rules-non-negotiable).
- **Risk tier.**
  - `regenerable`: caches, including Docker build cache unused for a week; fine to remove automatically
  - `rebuildable`: costs time to restore, e.g. `target/`, venvs
  - `review`: models, worktrees, scratch dirs, volumes; needs a person
  - `blocked`: a guard failed; never applied
- **Plan.** The findings you select, plus actions, fingerprints and an expiry time. Applying it re-runs every guard and skips anything whose fingerprint has changed.

## CLI (MVP)

```
dwhy [tui [PATH…] [-x | --cross-filesystems]]     # interactive TUI (default PATH: .)
dwhy scan [PATH…] [--json] [--snapshot] [-x | --cross-filesystems] # sizes + findings + unaccounted space (default PATH: .)
dwhy diff [PATH…] [--since last|<snapshot>|7d|<time>] [--json]     # growth since a snapshot
dwhy watch [PATH…] [--for 60s] [--json]           # live growth rate per directory/volume
dwhy explain <finding-id|path> [--json]           # evidence, guards, growth, recovery cost
dwhy plan [PATH…] [--tier regenerable|rebuildable|review] [--select ID|PATH,… | --free SIZE] [-o plan.json] [--json]
dwhy apply plan.json [--max-tier regenerable] [--confirm ID,…] [--yes] [--dry-run] [--json]
dwhy audit [--limit N] [--json]  # what apply did, newest first
dwhy doctor                                       # available tools, detectors, probes and permissions
dwhy guide                                        # version-matched quickstart for agents (stdout only)
```

Exit codes: `0` ok · `1` error (clap usage errors map to 1 so they do not clash with 2) · `2` some items were skipped · `3` refused by policy.

With `--json`, a command that fails or refuses before it has a report writes an [`ErrorReport`](../crates/dwhy-core/src/report.rs) on stdout (`kind` `usage`, `error` or `refused`, a `message`, an optional `hint`, and the `exit_code` it exits with); stderr says the same in text as without `--json`. A report already started on stdout stays the only document there: when `scan` or `diff` cannot save its `--snapshot`, or `apply` has run, the exit code and stderr tell the rest. `--help` and `--version` are not errors. `apply --json` adds `would_free` on a dry run and `audit_log` on a real run.

### TUI details

The scan stays on each root's filesystem by default. The explicit `-x` flag also accepts the spelling `--one-file-system`. Either spelling conflicts with `--cross-filesystems`, which allows the scan to descend into other mounted filesystems while still skipping pseudo-filesystems such as proc and sysfs.

The scan runs in the background and shows progress through the walk, filesystem accounting, detectors and probes. The browser lists multiple roots together. Rows are largest first, using allocated size by default. Within a directory, the `[files]` row measures direct non-directory entries. The current directory's own blocks are included in its allocated total only, so its rows can add up to less than 100% in allocated mode. The browser marks unreadable directories, read errors and skipped mounts where they affect the tree. If a marked directory has no measured rows, the browser shows a diagnostic in place of the empty label.

The header shows used space and capacity, along with the unaccounted figure where available. For a subtree it shows the scanned bytes. If more than three filesystems are reported, the header shows the first two and an overflow count. Press `f` to toggle the scrollable list of all filesystem figures. The tree status includes the total in the current view, scan diagnostics and the findings count.

Tab switches between the tree and the full-screen findings list. Findings are sorted by estimated reclaimable size, largest first, with ties sorted by path. Rows show tier, size, growth, detector and path. As the terminal narrows, the list drops the growth column first, then the detector column. Long paths are shortened in the middle. The header shows the active filter and the number shown out of the total when space permits. Press `t` to cycle through all, regenerable, rebuildable, review and blocked. The selection stays on the same finding if it still matches. The empty state distinguishes a scan with no findings from a tier with no matches. Detector failures appear in the status line when the filter shows findings (as a count when no detector name fits), or as scrollable errors when the list is empty.

Enter, Right or `l` opens the selected finding. The detail view wraps the finding's text in `dwhy explain` field order, including Postgres WAL evidence and notes when present. Esc, Backspace, Left or `h` returns to the list at the same selection. Tab returns directly to the tree. The view shows guards recorded by detectors. When the scan recorded none, it points to the full checks that run when a plan is made.

The TUI reads existing snapshots using the same finding growth rule as `dwhy scan` (see the Diff decision). The growth column shows `–` for findings without a rate. Detail distinguishes a missing baseline from an unavailable rate. The TUI saves no snapshots.

The findings views escape control characters and backslashes in paths, and variation selectors that do not change how the preceding character is drawn, so `app\u{fe0f}` cannot pass for `app`. The list marks paths that may have been converted from invalid UTF-8 with `!`, and detail warns that those paths are approximate. Detail withholds commands for these paths or when the command text contains the replacement character U+FFFD. Advice and recovery notes appear as prose. Commands that wrap or otherwise cannot be shown unchanged as one line of printable ASCII are labeled `preview — do not copy`.

Space marks or unmarks the selected finding when its row is visible. Marks stay through the tier filter and Tab. The header shows their count and total bytes, omitting bytes for an absolute path nested below another marked path in the scan's tree (a mount point scanned as its own root is not nested in the root above it). Only findings with removal actions can be marked, including blocked findings.

Pressing `p` resolves the saved roots again and scans them with the same filesystem and detector options. The TUI shows progress while the worker rescans and builds the plan. Esc or Tab can leave that view. Pressing `p` again with the same marks returns to its progress. With different marks, `p` waits for the worker to finish and then builds for the current marks. A result is discarded if the view is closed or the marks have changed when it finishes. Pressing `q` still quits. The worker selects the marked IDs that match fresh findings with a removal action and passes them to `plan::build` for the same selection rules, guards and fingerprints as `dwhy plan --select`. A mark whose fresh finding is advice only is left out and labeled “now advice-only” with the advice. The rescan runs without probes or growth. Its detection time sets the plan's creation and starts its validity window. A missing ID is labeled “gone since the scan” if its detector succeeded and the rescan covered its path. Otherwise it is labeled “not checked” with the reason: the detector failed or did not run, or the path is at or below a directory the rescan could not read, a scan error, or a mount point the rescan did not enter. If no marks match, the findings list shows a message. The tree and findings still show the original scan.

The preview shows the total estimated bytes freed, the creation time and effective expiry, then each item's tier, size, path, action and guards, followed by any blocked findings and their reasons. Commands follow the detail view's copy rules. The preview treats any item path containing U+FFFD as approximate, including in saved plans. Advice on blocked findings and notes that replace recovery commands appear as prose. Both previews check `plan::usable` as they render, so a refusal reason can appear while a plan is open. The banner uses the available space above the plan contents, keeping a row for the plan; with only one row, a shortened one-line banner takes its place. In a preview built from marks, Esc returns to the findings list with the marks kept.

In a preview built from marks, `w` asks where to save a new plan file, `./dwhy-plan.json` by default (relative to the working directory). Enter creates the file, Esc cancels, Backspace deletes, and Ctrl-U clears. The path prompt accepts `q` as text. Parent directories may be symlinks. The destination name must be unused, including by symlinks and non-regular entries. If it already exists, the prompt stays open so you can choose another name. The TUI creates the file with `O_CREAT|O_EXCL|O_NOFOLLOW`, follows the umask, and syncs the written contents. If a write fails, the new file can be left incomplete, in which case `dwhy apply` refuses it. A successful write produces the same bytes as `dwhy plan -o`. Apart from applying (below), this file is the only thing the TUI writes, and only on `w`.

`dwhy tui --plan FILE` opens an existing plan for preview without scanning. Since the plan carries its own roots, this mode conflicts with paths, `-x` (`--one-file-system`) and `--cross-filesystems`. It uses the same parser as `dwhy apply`. An unreadable or malformed file exits 1 before the terminal is touched.

In either preview, `x` opens the confirm dialog for a usable plan with at least one item. The status line explains why a plan cannot be applied. The dialog lists each item's tier, size, path and action using the detail view's command copy rules. The summary counts items and review confirmations and estimates reclaimable bytes from the plan, leaving out unticked review items, blocked items and advice-only items, which apply would not run. Like the plan's total, it counts an item nested below another item once, but counts a root the scan took on its own (the deepest of the plan's roots, or, in a one-filesystem scan, another device than the root whose walk measured the item; a plan item records that root's device as `scan_root_dev` when the item is in a btrfs subvolume the walk entered) separately, with or without the scan's tree. The estimate precedes the fresh apply checks. Use the arrows to select an item. Page Up and Page Down scroll through a long selected action with its header and any copy-rule notice kept in view. Other items on screen start at their header, and an item at the bottom edge shows its action only when its copy-rule notice fits whole. If there is insufficient room for the summary, selected item and recognizable path, any copy-rule notice, an action row or the key help, the dialog asks you to enlarge the terminal and disables Space, `y` and `d`.

Space toggles the selected `review` item's checkbox under the TUI tier policy above; with Ctrl or Alt it does nothing. Advice-only items, including `review` ones, get no checkbox, and Space on them or on a blocked item says nothing will run. `y` applies, `d` runs a dry run and Esc cancels. Both apply keys recheck plan usability. The worker uses the plan's scan options and the same re-detection, guards, execution and audit rules as `dwhy apply --yes`. In a `dwhy tui --dry-run` session, `y` also uses the Apply decision's dry-run behavior. The header shows `DRY RUN` on every screen and the dialog labels `y` “dry run”.

The apply worker shows progress through the rescan, the checks and the items being removed. Core runs cleanup commands with stdin from `/dev/null` and captures stdout and stderr. The failure reason can include the last nonblank stderr line from a command that failed. Quitting mid-apply (`q`, Ctrl-C or a signal) requests a stop. The worker lets the item in progress finish and skips remaining ready items when it observes the stop request before dispatch. It attempts an audit `end` line for each item skipped this way with “not run: apply was stopped before this item”. The TUI runs cleanup commands in their own process groups so a signal to the terminal foreground group leaves the current command running. The TUI waits for the worker and exits without showing results.

The results screen shows each item's outcome and reason, the exit status `dwhy apply` would give and the audit log path when available. It estimates the bytes freed or, for a dry run, the bytes the ready items would free, nesting items within the apply scan's roots as the plan's total does (`dwhy apply` uses the same totals for its summary and y/N question). Enter clears the marks and rescans with the same options. A `--plan` session uses its plan's roots, filesystem setting and detectors. The rescan leaves out a root that is missing when it looks the root up, including one below a path that is no longer a directory, and scans the remaining roots. Other errors, such as permission denied, still fail it. The status line lists a missing root at or below a path this apply removed as removed, and any other missing root as unavailable (an unmounted drive, say). When no root remains, the TUI shows “all scanned roots were removed” if this apply removed every one, “all scanned roots are unavailable” if it removed none, and that no scanned roots remain otherwise, then waits for `q`. Esc on the results returns to the dialog with confirmations kept after a dry run, an error before execution, or a report in which no item's action was started: only refusals, skips and failures before dispatch, such as an item whose audit `start` line could not be written.

Page Up and Page Down move by one screen, and Home and End go to either end. In the tree, findings list, detail, plan preview, confirmation and results, `k` and `j` also move up and down, and `g` and `G` go to the beginning and end. In the tree, Right and `l` open a directory, and Left and `h` go up to the parent. Ctrl-C also quits.

The TUI restores the terminal on exit, including after a panic. Quitting does not wait for a scan or plan build in progress: the TUI kills the read-only commands it started (git, `docker exec … psql`) and starts no more. It reports errors locating, opening or writing the audit log on stderr after restoring the terminal and exits 1. Otherwise, a normal quit exits 0 regardless of the apply status displayed on the results screen. On SIGHUP, SIGINT or SIGTERM it exits with `128 + signal number`.

### Policy config

```toml
# /etc/diskwhy/policy.toml (machine ceiling) and/or
# $XDG_CONFIG_HOME/diskwhy/policy.toml (else ~/.config/diskwhy/policy.toml)
max_tier = "regenerable"   # regenerable | rebuildable | review; never blocked
confirm = "flag"           # flag | interactive | never

[scratch]
paths = ["~/work/scratch", "/srv/scratch", "runs/run-*"]  # added to the built-in list
stale_days = 14            # at least 1; default 7
```

Every key is optional, and an unknown key is an error, so a typo cannot drop a limit. When both files exist they merge, each only tightening:

- `max_tier`: the lower of the two. Apply lowers `--max-tier` to it (the TUI's dialog asks for `review`), and records the lowered value as the report's and audit records' `max_tier`. Unlike `--max-tier`, it also refuses `review` items above it, even with `--confirm`: `max_tier = "rebuildable"` means no review item is applied. A refusal names the file that set it.
- `confirm`: the stricter of the two. `flag` (default) is `--confirm ID` per review item, as before. `interactive` also needs a person at the terminal: `dwhy apply` refuses review items with `--yes` or without a terminal, and the TUI's dialog counts. `never` refuses every review item.
- `scratch.paths`: the union, in order. Entries are absolute, `~/…`, or relative to the home directory; a last component ending in `*` is a prefix, as in the built-in list; `.`, `..`, empty entries and a bare `*` are errors.
- `scratch.stale_days`: the larger of the two.

**Trust boundary.** `--max-tier`, `--confirm` and the user's policy file guard against mistakes and accidental escalation, by a person or by an agent running as the same uid. They are not a security boundary: an agent with a shell can edit the user's files or pass any flag. The root-owned `/etc/diskwhy/policy.toml` sets a ceiling such an agent cannot raise through diskwhy, and `audit.jsonl` records how each apply was invoked (`max_tier`, `confirm`, `yes`, `tty`) for review with `dwhy audit`. An agent with a shell can still remove files without diskwhy. A hard boundary needs a non-shell client, such as `dwhy-mcp` (whose ceiling is a launch flag the model cannot pass), or an OS privilege boundary, such as a separate user.

### JSON contract

The [`diskwhy/v1` serde types](../crates/dwhy-core/src/report.rs) define the JSON contract (in scan output, `uid` is the effective uid alongside `root`, while `dwhy doctor --json` reports both the real `uid` and `euid`; `fs[].unaccounted` is `null` unless `full_coverage` is true). The pinned shapes include a [WAL finding](../crates/dwhy-core/tests/snapshots/json_shape__postgres_wal_evidence_shape.snap), [API-only WAL evidence](../crates/dwhy-core/tests/snapshots/json_shape__api_only_evidence_shape.snap) and [explain reports](../crates/dwhy-core/tests/snapshots/json_shape__explain_report_shape.snap).

The versioned CLI output is the contract for agents and the MCP server.

## Growth without a background job

1. **Snapshots.** `scan --snapshot` saves a compact record: directories of 100MB or more (counting hardlinked files once), Docker image/volume/cache sizes, `df` per filesystem, and the findings. They go to `~/.local/state/diskwhy/snapshots/`, gzip-compressed, and old ones are pruned (see Snapshots under Decisions taken). `diff` rescans and compares with a snapshot, ranking by growth rate (see Diff under Decisions taken), and `scan` puts a growth rate on findings.
2. **Signals that need no history.** Large files written in the last N days, which caught `statev2.sqlite` here. Probes for known patterns: database WAL vs data ratio, unbounded Docker `json-file` logs, journald, core dumps, `/tmp`.
3. **Watch.** Walks the roots and reads Docker's figures twice over a short window (`--for 60s`) and reports bytes per minute (see Watch under Decisions taken). This catches active runaways right away.
4. *(later)* A systemd user timer that runs `scan --snapshot` daily and alerts through `notify` when growth crosses a threshold.

## Safety rules (non-negotiable)

- Scans write nothing except their own state. Git commands run with `--no-optional-locks`.
- Every removal is either a tool-native command or a path removal limited to the finding's root. Symlinks are never followed out of that root, and nothing crosses a filesystem boundary.
- `diskwhy/v1` reports paths as UTF-8 and replaces invalid bytes with U+FFFD. A path or command built from that spelling can name a different, real path. Detection sets the tier to `blocked` and records a blocking `path-not-utf8` guard when a finding's path, action argv or text, recovery command, or recovery cost contains U+FFFD. This also covers names containing a literal U+FFFD. The action becomes advice to rename the path to valid UTF-8 and scan again, or to remove it by hand. A recovery command containing U+FFFD is replaced by a note. The finding keeps its ID, reported path, bytes and detector for accounting. The check runs before nesting, so findings inside a blocked finding can still be offered. Scan nesting uses the original filesystem paths. The same check runs again after probes (decided 2026-11-19, issue #61).
- `apply` refuses plans with U+FFFD in any scan root before rescanning (exit 3). When it evaluates an item, it skips it with `path-not-utf8` if the planned or freshly detected path or argv contains U+FFFD. It checks again immediately before executing the action. These skips use the normal skipped outcome, exit code and audit rules in the Apply decision.
- Filesystem fingerprints use measurements from the walk. For standalone Claude Code executables and VS Code Server `code-<commit>` files, the detector records the device, inode, size and mtime from the same stat without following the final symlink. That record is used only for a path the walk did not record; if the walk recorded the path with another device or inode, the identity check fails. The live identity check rejects missing or uncheckable paths, symlinks anywhere in a path, missing recorded identities and device or inode mismatches. The walker records a subdirectory's identity before opening it. A replacement between the stat and open that is reversed before the live check can escape detection (issue #63).
- `plan` checks the selected filesystem findings after the guards and after computing any eligible fingerprints. A failing root or descendant check adds a blocking `changed-since-scan` guard and puts the finding in `blocked`. A selected finding that a detector already blocked gets only the root check.
- The guards check each finding root and each repository they read against the walk before reading Git state. A changed root gets a blocking `changed-since-scan` and no Git guards. A changed repository blocks its finding as one Git could not check. A `.git` file whose `gitdir:` or `commondir` leads into a changed root or repository is not followed. A work tree in the scan that changed but is not gone may use any git directory, so `git-linked-worktrees` blocks every finding that holds a git directory.
- `apply` checks the root of an otherwise eligible finding against the fresh measurement before comparing fingerprints. For items still ready, it checks the root and descendants after running the guards and again just before dispatch. The guard batch includes all planned filesystem roots, so a skipped item can still block removal of Git metadata it depends on. Docker items are guarded only while ready. When a live identity check fails, `apply` skips the item and reports its detector guards and `changed-since-scan`. Path removal checks the root's device and inode once more through its opened parent.
- For both commands, descendant checks cover scanned directories with a `.git` marker and nested candidate paths. The planning candidates come from the selection eligible for pre-removal guards. Apply uses all items in the plan. During dispatch, a missing descendant is allowed when that exact path was the root of a successful removal earlier in the same run, or one of that root's checked descendants found missing right after it. A path that reappears blocks the enclosing item.
- Agents are limited by `--max-tier` (default `regenerable`) and the [policy config](#policy-config), whose `/etc` file is a ceiling nothing in diskwhy can raise. See the [Apply and TUI decisions](#decisions-taken) for the required per-item confirmation for `review` items, and the policy config's trust boundary for what these limits do not stop.
- Append-only audit log in `~/.local/state/diskwhy/audit.jsonl`, recording how each apply was invoked; `dwhy audit` reads it.
- No Trash or quarantine by default: on the same filesystem they **don't free space**. Optionally, quarantine can apply to `review` items, with a purge time.
- Guard tests: every guard has fixture tests (temporary git repos with unpublished commits, a process with its cwd inside the target, and so on) proving that it blocks.

## Architecture

```
crates/
  dwhy-core     scan engine, snapshot/diff/watch (growth), detectors, probes, guards, plan/apply, JSON types
  dwhy-cli      clap front end, JSON output, exit codes (binary: dwhy)
  dwhy-tui      ratatui + crossterm terminal interface
  dwhy-mcp      rmcp stdio server (binary: dwhy-mcp): scan/explain/diff/watch/plan/apply with the same policy
```

`dwhy-core::ops` holds the commands' orchestration (scan, diff, watch, explain, plan, and the rescan apply makes), so `dwhy` and `dwhy-mcp` give the same answers; each front end only renders. `dwhy-mcp` is a separate crate and binary so `dwhy` stays synchronous, without tokio or rmcp.

**MCP server.** Tools return the `diskwhy/v1` report as JSON text, or an `ErrorReport` with `isError` (`usage` for bad arguments, unknown ones included; `error`; `refused`). `scan` defaults to the summary report. The person launching the server sets `apply`'s ceiling (`--max-tier regenerable|rebuildable`) or removes it (`--read-only`); `apply` takes a plan and `dry_run` only, applies with no `--confirm` ids and no terminal (so `review` items are always refused), and the policy config lowers the ceiling as for `dwhy apply`. Audit records say `yes: true`, `tty: false`. The policy config is loaded on every call and fails closed. Blocking work runs on tokio's blocking pool; stdout carries only the protocol.

Crates likely needed: `clap`, `ratatui`, `crossterm`, `serde`/`serde_json`, `rayon` (or `jwalk`), `procfs`, `flate2` (gzip, pure Rust), `directories`, `time`, `insta` (snapshot tests).
