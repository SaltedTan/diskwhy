# diskwhy — scope and MVP design (draft)

> Working name. `diskwhy` (binary `dwhy`) is free on crates.io, as are `whyfull`, `diskdoc`, `tidyfs`, `bloatwatch`.

## Pitch

**"Why is my disk filling up, and what is safe to remove?"**

A Rust tool for Linux dev boxes, used over ssh. It finds what is big **and what is growing**, explains each item, checks whether it is safe to delete, and removes it the way the owning tool would. It has two interfaces over one engine:

- a **TUI** for people (ratatui; works in any ssh terminal)
- a **JSON CLI** for agents, built around *scan → plan → apply*, where an agent may apply a plan only within limits you set

The idea is to automate what was done by hand on pc-ubuntu on 2026-11-13: 36G free → 166G free, with one root cause (29G of Postgres WAL stuck behind a dead fake-S3 container) that no current cleaner would have found.

## What sets it apart from gdu, lysosome, Mole and others

1. **Growth, not just size.** A scan can keep a snapshot (`--snapshot`), so a later run can show what grew and how fast. The `watch` command measures growth rate within one session, and probes look for known runaway patterns. No background job is needed.
2. **Accounting for hidden space.** It reports the gap between what `df` says is used and what the scan could see (e.g. "70G you can't read — rerun with sudo"). It lists Docker images, volumes and build cache by name, and counts each hardlinked file once, so sizes reflect what deleting actually frees.
3. **Safety checks that look at real state**, not just name patterns:
   - commits that exist on no remote (not only unpushed relative to the upstream branch), in nested repos too
   - uncommitted or untracked files
   - processes whose working directory or open files are inside the target
   - paths a running container or Compose project depends on
   - age gates
4. **Tool-native removal, and stating the cost of recovery.** It uses `cargo clean`, `docker builder prune --filter until=…`, `git worktree remove` without force, `go clean -cache`, and so on. Each finding says what it costs to get back ("reinstall 4 venvs, ~10 min").
5. **Agents can act, but only within a policy.** Plans carry fingerprints and are re-checked when applied. Each risk tier has its own limit, and every action is written to an audit log.

| Trash (`trash`) | One finding per trash directory (the home trash, and `.Trash-<uid>` or `.Trash/<uid>` at mount roots), removed as a whole so `files/` and `info/` go together; the spec has file managers recreate it. `review`, or `blocked` with a `recent-delete` guard when anything was trashed in the last 7 days, going by the `DeletionDate` in `info/*.trashinfo` |
| Guards | `plan` and `apply` run guards before removal. `scan` skips them. A home scan takes about 0.4 s, with guard checks taking about 1.3 s for ~200 git worktrees inside findings. See the Explain decision for diagnostic use. A guard that cannot check (git missing or failing, Docker unreachable) blocks. Git guards skip repositories inside a cache (`CACHEDIR.TAG`) and do not apply to `user-cache` and `tool-versions` findings. Removing a linked worktree or submodule whose git directory is outside the finding keeps its branch's commits in the repository, so unpushed commits there only warn; commits on no branch block. When the git directory is inside the finding (a `.git` directory, a submodule of a superproject in it, a `--separate-git-dir` clone next to it), every commit on no remote blocks. Git directories without a `.git` entry (bare repositories, `--separate-git-dir` targets: a `HEAD` file plus `objects/` and `refs/`) are guarded too: commits on no remote block, and so do work trees outside the finding that use them. A bare or mirror clone has no remote-tracking refs, so it always blocks. One whose `HEAD` the enclosing work tree tracks (a test fixture in a source tree) is part of that repository's history and is skipped. Git runs none of the repository's own programs: `core.fsmonitor` and every configured filter driver are switched off, and `git status` does not look inside submodules (each is checked as a repository of its own), though a submodule checked out at a different commit than recorded still makes the superproject dirty |
| Plans | `dwhy plan` selects by tier ceiling (`--tier`, default `regenerable`, the same as `apply`'s default `--max-tier`) and by finding id or path (`--select`, which lifts the default ceiling; with `--tier` too, a finding must match both). A `--select` entry that names no finding, or only an advice-only one, is an error. Guards run on the selection only. A finding a guard blocks, or a detector-blocked one that `--select` names, goes to the plan's `blocked` list, never its items; advice-only findings are never selected. `plan` exits 2 (the plan is still written) when a finding `--select` named ends up in `blocked`; a finding only the tier ceiling picked that a guard blocks is listed but keeps exit 0, so `dwhy plan -o p && dwhy apply p` works. Each item carries a fingerprint: the root's device and inode, the newest mtime under it, its size in buckets of a quarter of a doubling, HEAD plus a hash of `git status` (branch headers left out) when the root is a git work tree, and for Docker the image or container id, or a volume's name and creation time (build cache has none, so only its size counts). A plan expires an hour after it is made (an edited `expires_at` cannot extend that) and is refused on another host or uid. `apply` does not trust a plan's actions or tiers: it rescans the plan's roots, re-detects, re-runs the guards and acts on the fresh finding with each item's id, skipping it when the fresh tier, action or fingerprint differs. An edited plan can go stale but cannot widen what `apply` may do (decided 2026-11-16) |
| Apply | `--max-tier` defaults to `regenerable` for everyone; `--max-tier rebuildable` lets rebuildable items through. A `review` item needs `--confirm <id>` for that item, which is enough on its own (it never lifts a rebuildable item above the ceiling); `blocked` is never applied. Without `--yes` on a terminal, apply lists what it will remove and asks y/N, then rescans and re-checks before removing; only items shown and still ready run. Without `--yes` and with no terminal it refuses (exit 3). `--dry-run` shows everything, removes nothing and writes no audit line. Ready items run deepest path first (pseudo-paths last). A path removal walks from `/` with `O_NOFOLLOW`, refuses a symlink root, a root that is not the plan's inode, and a root with a mount point at or below it, and stops at an entry on another device; a read-only directory of the user's own inside the root gets `u+rwx` so it can be emptied. Each item gets one outcome: removed, failed, skipped (gone, blocked, changed), refused (tier or confirmation) or would_remove (dry run). The exit code is the worst: 1 failed, then 3 refused, then 2 skipped, else 0. The audit log (`$XDG_STATE_HOME/diskwhy/audit.jsonl`, default `~/.local/state/diskwhy/audit.jsonl`, mode 0600) gets a `start` line before each removal and an `end` line with its outcome, plus an `end` line for each skipped or refused item; a removal whose `start` line cannot be written does not run (decided 2026-11-16) |
| Snapshots | Only `scan --snapshot` saves one; `scan` alone still writes nothing. A snapshot is gzip-compressed `diskwhy/v1` JSON (`flate2` with the pure-Rust `miniz_oxide` backend, so the static musl build needs no C compiler; zstd was the first idea, and gzip compresses these files about as well) in `$XDG_STATE_HOME/diskwhy/snapshots/` (default `~/.local/state/diskwhy/snapshots/`), named `<YYYYMMDDTHHMMSSZ>-<scope>[-<n>].json.gz` (`-<n>` only when that second's name is taken), where the scope hashes the host, uid, scan roots (in any order) and `-x`. It records directories of 100 MiB or more (allocated, each hardlinked file counted once), [Docker usage and object records](../crates/dwhy-core/src/report.rs), `df` per filesystem, the detectors that ran, the mount points the walk did not enter, and each finding's id, detector, path, bytes and tier (so growth can be put on findings and `explain` can turn an id into a path). A home directory on pc-ubuntu gives ~1,000 directories and ~140 findings, ~32 KB. Saving prunes, per scope: everything from the last 48 hours is kept, then the newest per UTC day up to 90 days; older ones are deleted. A new snapshot never replaces a file, and pruning removes only regular files with a snapshot name. When saving fails, the scan report is still printed and `scan` exits 1; when only pruning fails after the snapshot is saved, `scan` warns and exits 0 (decided 2026-11-16) |
| Diff | `diff` rescans now and compares with a saved snapshot (`--snapshot` also saves the fresh scan). Without `PATH` it takes the newest snapshot of this host and uid matching `--since`, whatever its roots, and rescans those roots with that snapshot's `-x`; with `PATH`, only snapshots of exactly those roots and `-x` count. `--since` takes `last` (the default), a snapshot id or file (whatever its roots; another host or uid is an error), a duration (the newest at least that old) or an RFC 3339 time (the newest taken by then). Only paths both scans walked are compared: inside the roots of both, and not at or below a mount point either skipped (each snapshot records the mount points its walk did not enter; one saved without that list counts as having skipped none). When the two differ in `-x`, a directory above a mount point one side skipped and the other entered is left out too, since its totals cover different ground; with the same `-x`, neither side's totals include a skipped mount, so a mount that appeared or went away between them leaves its ancestors compared. `notes` names a mount point only when a directory or finding either side recorded was left out because of it. It lists `df` used per filesystem, directories, Docker objects (images and containers by id, volumes by name, build cache; an object whose size the daemon did not compute on either side is left out) and findings by id (one present on one side only is listed only when its detector ran on both), each ranked by bytes per day; changes under `--min-change` (default 10M) are left out. A directory's change goes to the deepest directory that holds most of it: a directory is dropped when the nearest listed directory below it changed by more than half as much in the same direction, so entries can still nest when growth is spread out; `watch` uses the same rule. A directory new above the snapshot's 100 MiB threshold counts the threshold as its earlier size, so its growth is a lower bound (`at_least`). `scan` and the TUI set finding growth from the newest readable snapshot at least an hour old with the same host, uid, roots and filesystem traversal setting. They match by finding id and report bytes per day. Rates scaled from a shorter window are mostly noise (decided 2026-11-16) |
| Watch | `watch` walks the roots in full at both ends of the window, every directory recorded, and reads Docker image, container, volume and build cache sizes from `GET /system/df` at both ends (volumes under /var/lib/docker are root-only on disk); `--no-docker` skips Docker. The second walk starts `--for` (default 60s, at least 1s) after the first one started, or right away if the first took longer, and rates are bytes per minute over the measured time between the two starts. It also lists `df` used per filesystem. Changes under `--min-change` (default 1M: about 1.4 GiB a day over a minute) are left out. Directories use `diff`'s deepest-directory rule and are compared only where both samples walked, using a fresh mount table for each sample. Paths unreadable or affected by a scan error in either sample, and directories below them, are excluded. Ancestors of paths that fail in only one sample are excluded within both samples' roots too; paths failing in both samples do not by themselves exclude ancestors. A mount skipped in one sample only also leaves out directories above it within both samples' roots, unlike `diff` (decided 2026-11-18). If either sample deduplicated hardlinks and either the failed-path set or skipped-mount set changes, all directory rates are suppressed because attribution can move between siblings; filesystem and Docker comparisons remain available. Notes explain coverage exclusions, naming failed paths and changed mounts when they kept recorded directories out. If scan errors exceed the recorded error paths, `watch` fails instead of comparing unknown coverage. Docker is compared only when figures are available at both ends; otherwise a note explains why. `watch --json` uses the additive `diskwhy/v1` `WatchReport` contract defined in [report.rs](../crates/dwhy-core/src/report.rs). It writes nothing; Ctrl-C ends the process (decided 2026-11-16 and 2026-11-18) |
| Explain | An argument is a finding id if it is exactly `f_` followed by 12 lowercase hex digits. Use `./f_…` for a file named like an id. Other arguments are paths, including Docker pseudo-paths. An id resolves through the newest snapshot of this host and uid that lists it, regardless of roots. If no snapshot lists the id, `explain` exits 1 and suggests passing the path or saving snapshots with `dwhy scan --snapshot`. If snapshot state is unavailable, it still suggests passing the path. Filesystem paths must be UTF-8, including after making them absolute and resolving the parent. Findings with paths that can be confused with a lossy spelling in the walked tree are excluded. Filesystem walks stay on one filesystem. For a directory, detectors normally see the parent walk. This gives `cargo-target` and `node-modules` their project context. Layouts needing context farther up can be missed (issue #50). The command scans `/`, files and symlinks on their own. It also scans the path on its own and adds a note when the path is a mount point (a mount-table entry or a different device from its parent), its parent cannot be opened, or the parent's walk lacks the path. Docker pseudo-paths skip the walk and use only Docker detectors. `--detectors` limits the detector selection. The command matches the exact path before applying the scan nesting rule. A saved filesystem finding must match its id at that path. A path query prefers the cheapest tier, then detector name. With no match, it reports any measured size and applies the scan nesting rule to the list of findings within the query scope. For a direct path query, the text report also says `no detector claims this path`. An id whose saved path contains U+FFFD (v1 snapshots store non-UTF-8 paths lossily) is refused with exit 1 and a hint to pass the real path. For an unmatched saved filesystem id, a metadata lookup of the saved path must report a missing path or a non-directory ancestor to mark it gone. For a saved Docker image or container, explain checks the immutable id recorded in the snapshot before picking a finding. If a rename or retag changes the object's pseudo-path, explain looks for the saved detector's finding at the current pseudo-path and adds a `renamed: now <name>` note. A saved volume matches by name. A different creation time confirms a replacement when both the snapshot and daemon provide one. If the live daemon omits a listed volume's creation time, a matching finding can still be shown. The report omits its growth and includes a note about the missing time. Without a saved Docker object id or volume creation time, explain falls back to the saved name, tag or short id and adds an `identity not checked` note when the daemon answers. If the saved object is absent and a different object now holds the saved name or tag, explain reports the saved finding gone. Its note gives the replacement's short id (creation time for a volume) and suggests running `dwhy explain <path>` to inspect it. Explain also omits growth across a detected replacement and includes a note. The saved Docker finding is also gone when the relevant list shows that the object is absent, or for build cache when its list is empty. An explicit empty or null list counts as empty. A missing list or unreachable daemon leaves presence unknown. An existing path without a current finding and an inconclusive presence check each get a note. Probes and guards run only for the selected finding. Growth uses the newest one-filesystem snapshot from the same host and uid that lists the finding and is at least an hour old at the start of the rescan, regardless of roots. The command is read-only and exits 0 when it reports and 1 on an error. See [`ExplainReport`](../crates/dwhy-core/src/report.rs) for the additive JSON contract (decided 2026-11-16 and 2026-11-18). |

They prefer a shared network, then a running container, then the same Compose project. During host lookup, a 404 skips a disappeared container. With archiving enabled (`on` or `always`), SQL evidence of failures at or after the latest success, or failures with no recorded success, prompts repair advice. API-only evidence prompts repair advice when the tail contains failures, a matched target has stopped, and archiving is not known to be off. Repair advice names an exited or dead target to restore when there is one. With SQL evidence of failure and no stopped match, it suggests fixing `archive_command` and offers starting the target as an option if a host lookup found no match. ### Recommendation: root vs user

- **Run as your user by default.** Everything works without sudo.
- **Report the gap.** If `df` used minus scanned bytes is larger than a threshold, show an "unaccounted N GB" item with the likely places (`/var/lib/docker`, `/var/log`, other users' homes) and the command to rerun with sudo.
- **Running under sudo is supported, not required.** System detectors (journald vacuum, old snap revisions, old kernels, apt cache) are enabled only when running as root.
- **Never touch other users' files** unless running as root *and* `--all-users` is passed.
- **Docker** is used through its socket and CLI. Being in the `docker` group is already root-equivalent, so Docker findings default to the `review` tier. The exception is build cache unused for a week, which is `regenerable`: it is a cache, `docker builder prune --filter until=168h` removes only those records, and the cost is re-running build steps (issue #2).

### Recommendation: static binary

- **Ship static musl builds** (x86_64 and aarch64) as GitHub release assets. Rust makes this cheap, and ssh boxes run all sorts of glibc versions. A `.deb` and `cargo install` come later.
- **No runtime dependencies are required.** It calls optional external tools (`git`, `docker`, `cargo`, `go`, `journalctl` and the package managers whose caches `user-cache` reports; `dwhy doctor` lists them all) when they exist. A missing tool disables only the detectors and probes that depend on it, and `dwhy doctor` explains why.
- **Shell out to `git`** instead of linking libgit2/gix. This matches git's own behaviour exactly (worktrees, submodules, safe.directory) and keeps the binary small.

## Main concepts

- **Scan.** A parallel, single-filesystem (`-x`) walk. It counts each hardlink once by (dev, inode) and records allocated vs apparent bytes. Unreadable directories are recorded, not skipped silently.
- **Detector.** Recognises one kind of reclaimable thing and turns it into a **finding**, e.g. `cargo-target`, `node-modules`, `venv`, `user-cache` (go/npm/uv/pip/HF/playwright), `git-worktree`, `stale-tree` (scratch dirs by age), `tool-versions`, `trash`, `docker-image`, `docker-build-cache`, `docker-container`, `docker-volume`, `journald`.
- **Probe.** Adds evidence that explains why a finding is big or growing. See [Decisions taken](#decisions-taken).
- **Guard.** A check that runs before removal, ending in pass, warn or block, with evidence: `git-unpublished`, `git-dirty`, `git-linked-worktrees`, `in-use-cwd`, `in-use-open`, `container-mount`, `recent-write`, `git-ignored-only` (not built yet).
- **Risk tier.**
  - `regenerable`: caches, including Docker build cache unused for a week; fine to remove automatically
  - `rebuildable`: costs time to restore, e.g. `target/`, venvs
  - `review`: models, worktrees, scratch dirs, volumes; needs a person
  - `blocked`: a guard failed; never applied
- **Plan.** The findings you select, plus actions, fingerprints and an expiry time. Applying it re-runs every guard and skips anything whose fingerprint has changed.

## CLI (MVP)

```
dwhy scan [PATH…] [--json] [--snapshot] [-x]      # sizes + findings + unaccounted space
dwhy diff [PATH…] [--since last|<snapshot>|7d|<time>] [--json]  # growth since a snapshot
dwhy watch [PATH…] [--for 60s] [--json]           # live growth rate per directory/volume
dwhy explain <finding-id|path> [--json]           # evidence, guards, growth, recovery cost
dwhy plan [PATH…] [--tier regenerable|rebuildable|review] [--select ID|PATH,…] [-o plan.json] [--json]
dwhy apply plan.json [--max-tier regenerable] [--confirm ID,…] [--yes] [--dry-run] [--json]
dwhy doctor                                       # available tools, detectors, probes and permissions
```

Exit codes: `0` ok · `1` error · `2` some items were skipped because of a guard or changed fingerprint · `3` refused by policy.

### TUI details

The scan stays on each root's filesystem by default. The explicit `-x` flag also accepts the spelling `--one-file-system`. Either spelling conflicts with `--cross-filesystems`, which allows the scan to descend into other mounted filesystems while still skipping pseudo-filesystems such as proc and sysfs.

The scan runs in the background and shows progress through the walk, filesystem accounting, detectors and probes. The browser lists multiple roots together. Rows are largest first, using allocated size by default. Within a directory, the `[files]` row measures direct non-directory entries. The current directory's own blocks are included in its allocated total only, so its rows can add up to less than 100% in allocated mode. The browser marks unreadable directories, read errors and skipped mounts where they affect the tree. If a marked directory has no measured rows, the browser shows a diagnostic in place of the empty label.

The header shows used space and capacity, along with the unaccounted figure where available. For a subtree it shows the scanned bytes. If more than three filesystems are reported, the header shows the first two and an overflow count. Press `f` to toggle the scrollable list of all filesystem figures. The tree status includes the total in the current view, scan diagnostics and the findings count.

Tab switches between the tree and the full-screen findings list. Findings are sorted by estimated reclaimable size, largest first, with ties sorted by path. Rows show tier, size, growth, detector and path. As the terminal narrows, the list drops the growth column first, then the detector column. Long paths are shortened in the middle. The header shows the active filter and the number shown out of the total when space permits. Press `t` to cycle through all, regenerable, rebuildable, review and blocked. The selection stays on the same finding if it still matches. The empty state distinguishes a scan with no findings from a tier with no matches. Detector failures appear in the status line when the filter shows findings, or as scrollable errors when the list is empty.

Enter, Right or `l` opens the selected finding. The detail view wraps the finding's text in `dwhy explain` field order, including Postgres WAL evidence and notes when present. Esc, Backspace, Left or `h` returns to the list at the same selection. Tab returns directly to the tree. The view shows guards recorded by detectors. When the scan recorded none, it points to the full checks that run when a plan is made.

The TUI reads existing snapshots using the same finding growth rule as `dwhy scan` (see the Diff decision). The growth column shows `–` for findings without a rate. Detail distinguishes a missing baseline from a finding absent from the baseline. The TUI saves no snapshots.

The findings views escape control characters and backslashes in paths. The list marks paths that may have been converted from invalid UTF-8 with `!`, and detail warns that those paths are approximate. Detail withholds action and recovery text for these paths or when that text contains the replacement character U+FFFD. Commands that wrap or otherwise cannot be shown unchanged as one line of printable ASCII are labeled `preview — do not copy`.

Space marks or unmarks the selected finding. Marks stay through the tier filter and Tab, and the header shows how many findings are marked and their bytes, each counted once when one marked finding is inside another. Advice-only findings cannot be marked. Blocked findings can and appear as blocked in the preview. Pressing `p` rescans the same roots with the same filesystem and detector options. The worker shows progress while rescanning, detecting, and building the plan, and `q` still quits. Core `plan::build` uses the fresh findings as `dwhy plan --select <ids>` does, with guards, fingerprints, and an expiry one hour after detection. The preview lists missing marks as “gone since the scan”. If all marks are gone, the findings list shows a message. The tree and findings still show the original scan. The preview shows the total estimated bytes freed and the expiry, then each item's tier, size, path, action and guards, followed by any blocked findings and their reasons. Esc returns to the findings list with the marks kept. Commands follow the detail view's copy rules.

In the preview, `w` asks where to write the plan, `./dwhy-plan.json` by default (relative to the working directory). Enter writes, Esc cancels, Backspace deletes and Ctrl-U clears; `q` is text there. An existing regular file needs `y` to overwrite, and `n` returns to the path. Parent directories may be symlinks. The final component must be absent or a regular file. A new file is created with `O_EXCL` and follows the umask. An overwrite stages the plan in a private file in the same directory, rechecks the destination's device and inode, and preserves its permission bits when publishing by rename. If the destination changed, the prompt stays open. The content is byte for byte what `dwhy plan -o` writes. This file is the only thing the TUI writes, and only on `w`.

`dwhy tui --plan FILE` skips the scan and opens a plan file in the preview. It conflicts with paths, `-x` and `--cross-filesystems`, since the plan carries its own roots. The file is read and parsed as `dwhy apply` reads it, and an unreadable or malformed file exits 1 before the terminal is touched. When `plan::usable` refuses the plan here (expired, another host or another uid), the preview still shows it under a banner giving the reason.

Page Up and Page Down move by one screen, and Home and End go to either end. In the tree, findings list and detail, `k` and `j` also move up and down, and `g` and `G` go to the beginning and end. In the tree, Right and `l` open a directory, and Left and `h` go up to the parent. Ctrl-C also quits.

The TUI restores the terminal on exit, including after a panic. On SIGHUP, SIGINT or SIGTERM it exits with `128 + signal number`.

## Growth without a background job

1. **Snapshots.** `scan --snapshot` saves a compact record: directories of 100MB or more (counting hardlinked files once), Docker image/volume/cache sizes, `df` per filesystem, and the findings. They go to `~/.local/state/diskwhy/snapshots/`, gzip-compressed, and old ones are pruned (see Snapshots under Decisions taken). `diff` rescans and compares with a snapshot, ranking by growth rate (see Diff under Decisions taken), and `scan` puts a growth rate on findings.
2. **Signals that need no history.** Large files written in the last N days, which caught `statev2.sqlite` here. Probes for known patterns: database WAL vs data ratio, unbounded Docker `json-file` logs, journald, core dumps, `/tmp`.
3. **Watch.** Walks the roots and reads Docker's figures twice over a short window (`--for 60s`) and reports bytes per minute (see Watch under Decisions taken). This catches active runaways right away.
4. *(later)* A systemd user timer that runs `scan --snapshot` daily and alerts through `notify` when growth crosses a threshold.

## Safety rules (non-negotiable)

- Scans write nothing except their own state. Git commands run with `--no-optional-locks`.
- Every removal is either a tool-native command or a path removal limited to the finding's root. Symlinks are never followed out of that root, and nothing crosses a filesystem boundary.
- `apply` re-runs all guards, compares fingerprints (inode, newest mtime, size bucket, git HEAD plus a status hash) and refuses expired plans.
- Agents are limited by `--max-tier` (config default `regenerable`). See the [Apply and TUI decisions](#decisions-taken) for the required per-item confirmation for `review` items.
- Append-only audit log in `~/.local/state/diskwhy/audit.jsonl`.
- No Trash or quarantine by default: on the same filesystem they **don't free space**. Optionally, quarantine can apply to `review` items, with a purge time.
- Guard tests: every guard has fixture tests (temporary git repos with unpublished commits, a process with its cwd inside the target, and so on) proving that it blocks.

## Architecture

```
crates/
  dwhy-core     scan engine, snapshot/diff/watch (growth), detectors, probes, guards, plan/apply, JSON types
  dwhy-cli      clap front end, JSON output, exit codes (binary: dwhy)
  dwhy-tui      ratatui + crossterm tree browser and findings (M4a–M4b)
  dwhy-mcp      (later) rmcp server exposing scan/explain/plan/apply with the same policy
```

Crates likely needed: `clap`, `ratatui`, `crossterm`, `serde`/`serde_json`, `rayon` (or `jwalk`), `procfs`, `flate2` (gzip, pure Rust), `directories`, `time`, `insta` (snapshot tests).
