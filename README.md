# diskwhy

**Why is my disk filling up, and what is safe to remove?**

`diskwhy` (binary `dwhy`) is a Rust tool for Linux dev boxes and servers, used over ssh. It finds what is big *and what is growing*, explains each item, checks whether it is safe to delete, and removes it the way the owning tool would. It has a TUI for people and a JSON CLI (scan → plan → apply) that agents can drive within limits you set.

Status: pre-MVP, private. See [docs/DESIGN.md](docs/DESIGN.md) for scope and milestones. M0 (scanner, `diskwhy/v1` JSON types, `doctor`) and M1 (detectors) are in place. M2 (guards, `plan`, `apply`) is built: an agent can clear `regenerable` items on its own and is refused `review` ones. M3 (growth) has started: `scan --snapshot` keeps a history of scans, `diff` shows what grew since one, `watch` measures what is growing right now, the `postgres-wal` probe explains a Postgres volume full of WAL, and `explain` shows everything known about one finding.

## Usage

```
dwhy scan [PATH…] [--json] [-x | --cross-filesystems] [--min-size SIZE] [--depth N] [--top N]
          [--no-detectors | --detectors NAME,…] [--max-findings N] [--snapshot]
dwhy diff [PATH…] [--since last|ID|FILE|24h|7d|TIME] [--json] [--snapshot] [--min-change SIZE]
          [--cross-filesystems] [--no-detectors | --detectors NAME,…] [--top N]
dwhy watch [PATH…] [--for 60s] [--json] [--min-change SIZE] [-x | --cross-filesystems] [--no-docker] [--top N]
dwhy explain ID|PATH|docker://… [--json] [--detectors NAME,…]
dwhy plan [PATH…] [--tier regenerable|rebuildable|review] [--select ID|PATH,…] [-o FILE] [--json]
          [-x | --cross-filesystems] [--detectors NAME,…]
dwhy apply PLAN [--max-tier regenerable|rebuildable|review] [--confirm ID,…] [--yes] [--dry-run] [--json]
dwhy doctor [--json]
```

- `scan` walks in parallel, never follows symlinks, stays on one filesystem unless `--cross-filesystems` is given, and counts each hardlinked inode once. Sizes are allocated bytes (`st_blocks`), which is what deleting frees; apparent sizes are reported too.
- Directories it cannot read are listed, not skipped silently. When a scan root is a mount point, the report includes `df` figures and an **unaccounted** figure (`df` used − scanned), with likely locations and a `sudo` rerun command when the gap is large.
- After measuring, `scan` lists **findings** from the detectors. Each finding has a risk tier, a reason, a suggested action and a recovery cost. The action can be a tool-native removal command, path removal or advice. Built so far: `cargo-target`, `node-modules` (the outermost `node_modules` next to a `package.json` whose project or workspace root has a lockfile; the recovery is `npm ci`, `pnpm install`, `yarn install` or `bun install`, chosen by that lockfile), `venv` (a directory holding `pyvenv.cfg`; the recovery comes from the project files next to it, such as `uv sync` for a `uv.lock`, and a venv with no project file is `review`, with the command to record its packages first), `user-cache` (pip, uv, npm/npx, pnpm, yarn, Go, Cargo, Playwright, Hugging Face; a cache written in the last 24 hours is shown as `blocked`, not offered), `git-worktree` (linked worktrees with nothing written for 14 days, removed with `git worktree remove` and never `--force`, and worktrees whose directory is gone, cleared with `git worktree prune`; all `review`, locked ones `blocked`), `stale-tree` (directories in a scratch location with nothing written for 7 days, all `review`; the built-in locations are `~/scratch`, `~/tmp`, `~/.t3/scratch` and `~/.t3/scratch-*`, and any directory becomes one when it holds a `.dwhy-scratch` file (an empty one is enough); a location stale as a whole is one finding), `tool-versions` (rustup toolchains, uv and pyenv Pythons, nvm and fnm Node versions, `~/sdk` Go SDKs, VS Code Server versions, and old Claude Code, Codex and T3 runtime versions that are not the default (or the version in use or run by a process), not pinned by a project in the scan, not used by a scanned venv and not the newest of their kind; `rebuildable`, removed with the tool's own uninstall command where it has one), `trash` (the home trash and `.Trash-<uid>`/`.Trash/<uid>` at mount roots, one finding per trash directory; `review`, or `blocked` when something was trashed in the last 7 days, going by each item's `DeletionDate`) and the Docker detectors (`docker-image`, `docker-build-cache`, `docker-container`, `docker-volume`). Docker findings are `review`, except build cache unused for a week, which is `regenerable`. The Docker ones read the Engine API socket and also put Docker's measured usage on the unaccounted-space hints. Every M1 detector is built. `scan` removes nothing and runs no guards.
- `scan --snapshot` also saves a compact record of the scan for measuring growth: directories of 100 MiB or more (each hardlinked file counted once), Docker images, containers, volumes and build cache with their sizes, `df` per filesystem, and each finding's id, path, size and tier. Snapshots are gzip-compressed JSON (`zcat FILE | jq` reads one) in `~/.local/state/diskwhy/snapshots/` (`$XDG_STATE_HOME` if set), about 30 KB for a home directory. Saving one prunes old ones, separately for each set of scan roots: every snapshot from the last 48 hours is kept, then the newest of each day up to 90 days, and older ones are deleted. Without `--snapshot`, `scan` writes nothing. When a snapshot of the same roots at least an hour old exists, `scan` puts a growth rate (bytes per day since that snapshot) on each finding it also lists.
- `diff` rescans now and compares with a snapshot: by default the newest one, and without `PATH` it rescans that snapshot's roots (with `PATH`, only snapshots of exactly those roots count; `--cross-filesystems` needs `PATH`). `--since` takes a snapshot id or file, a duration (`24h`, `7d`: the newest snapshot at least that old) or an RFC 3339 time (the newest taken by then). Only paths both scans walked are compared: inside the roots of both, and not at or below a mount point either one did not enter; when one side was `-x` and the other was not, directories above a mount point only one side entered are left out too. A note names the mount points that kept something either side recorded out. It lists `df` used per filesystem, then directories, Docker images, containers, volumes and build cache, and findings (matched by id), each ranked by growth rate in bytes per day, with new, gone and shrinking entries too; changes under `--min-change` (default 10M) are left out. A directory's change is shown on the deepest directory that holds most of it: a directory is left out when one below it changed by more than half as much in the same direction. A directory that was under the snapshot's 100 MiB threshold shows its growth as a lower bound (`≥`). `--snapshot` also saves the fresh scan. `diff` writes nothing else.
- `watch` measures growth now: it walks the roots (default: the current directory) and asks Docker for its figures (`GET /system/df`; `--no-docker` skips it), waits, and does both again, the second walk starting `--for` (default 60s) after the first one started, or right away if the first took longer. It lists `df` used per filesystem, directories and Docker images, containers, volumes and build cache, each ranked by growth rate in bytes per minute over the measured time between the two starts, with new, gone and shrinking entries too; changes under `--min-change` (default 1M, about 1.4 GiB a day over a minute) are left out. Each directory change is shown on the deepest directory that holds most of it, as in `diff`. See the Watch decision in [docs/DESIGN.md](docs/DESIGN.md#decisions-taken) for exclusions when read or mount coverage changes. `watch` writes nothing.
- `explain` explains one finding in full: its detector, size, tier and reason, the probe's evidence, every guard with its result, its growth rate, the action that would remove it and the cost of getting it back. Give it a finding id (`f_…`; the newest snapshot from `scan --snapshot` that lists the id gives its path), a path, or a Docker pseudo-path such as `docker://volume/NAME`. It rescans just that path, on one filesystem, runs the detectors (`--detectors` limits them), then the probes and the guards on the finding there. When no detector claims the path, it shows the path's size and the findings inside it. When an id's finding is no longer detected, it says the finding is gone and shows what is at the path now. Growth comes from the newest snapshot at least an hour old that lists the finding. `explain` writes and removes nothing.
- Use `dwhy scan --detectors docker-volume` to focus on Docker volumes. The read-only `postgres-wal` probe adds WAL and archiving evidence to eligible findings. See the [probe behavior](docs/DESIGN.md#decisions-taken).
- `plan` scans, runs the detectors, selects findings and writes a plan for `dwhy apply` (`-o FILE`; `--json` prints it). It selects by tier (`--tier`, `regenerable` by default, the same as `apply`'s default) and by finding id or path (`--select`, which lifts the default tier; with `--tier` too, a finding must match both). It then runs the **guards** on what it selected: a process with its working directory or a file open inside, uncommitted changes or commits on no remote in a git repository inside, worktrees outside that would break, a running container using a volume. A finding a guard blocks is listed under `blocked` and never planned; when one that `--select` named is blocked, `plan` still writes the plan but exits 2. Each item carries a fingerprint (the root's inode, the newest mtime under it, its size bucket, HEAD and a `git status` hash for a git work tree, the Docker object id), and the plan expires an hour after it is made. `plan` removes nothing.
- `apply` carries out a plan. It does not take the plan file's word for what to run: it rescans the plan's roots, re-runs its detectors and the guards, and acts on the finding detected now with each item's id. An item is skipped (exit 2) when it is gone, a guard or detector blocks it, or its tier, action or fingerprint changed; it is refused (exit 3) when its tier is above `--max-tier` (default `regenerable`; `--max-tier rebuildable` lets rebuildable items through) or it is a `review` item whose id `--confirm` did not name (`--confirm` alone lets that one review item through). `blocked` is never applied. Removal is the tool's own command (run as argv, never through a shell) or a path removal limited to the finding's root that never follows a symlink and never crosses a filesystem boundary. On a terminal, `apply` lists what it will remove, asks y/N, and checks everything again before removing; with no terminal it refuses unless `--yes` is given. `--dry-run` shows everything and removes nothing. An expired plan, or one from another host or user, is refused (exit 3). Every removal writes a `start` line before it runs and an `end` line with its outcome to `~/.local/state/diskwhy/audit.jsonl` (`$XDG_STATE_HOME` if set), and skipped or refused items get an `end` line; a removal whose `start` line cannot be written does not run. When several things happen the exit code is the worst: 1 failed, then 3 refused, then 2 skipped.
- `doctor` shows whether you are root, which optional tools (`git`, `docker`, `cargo`, `rustup`, `go`, `uv`, `pyenv`, `pip`, `npm`, `pnpm`, `yarn`, `fnm`, `journalctl`) are on `PATH`, what they enable, and whether each detector and probe is available.

Exit codes: `0` ok, `1` error (usage errors and failed removals included), `2` items skipped by a guard or a changed fingerprint, `3` refused by policy.

## Building

```
cargo build --release                                              # target/release/dwhy
cargo build --release --target x86_64-unknown-linux-musl -p dwhy-cli  # static binary
```

The workspace has `crates/dwhy-core` (engine and JSON types) and `crates/dwhy-cli` (the `dwhy` binary).
